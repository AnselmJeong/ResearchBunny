# 본문 구절 색인 구현 기록 (1단계)

ResearchBunny를 서지관리 앱에서 근거를 찾아 답하고 보고서를 쓰는 연구 앱으로 넓히는 첫 단계다. 서고 PDF의 본문을 문단 크기의 구절로 나눠 색인하고, 질문이나 키워드로 구절을 찾아 원문의 그 쪽을 연다. 2단계(근거를 달아 답하기)와 3단계(질문에서 시작하는 보고서)는 이 색인 위에서 검색된 구절을 AI에 보내고 인용한다.

## LEANN을 쓰지 않은 이유

[LEANN](https://github.com/StarTrail-org/LEANN)은 임베딩을 저장하지 않고 질의 때 다시 계산해 저장 공간을 줄인다. 이 서고(PDF 9,055개, 41만 7천 구절)에서는 디스크가 병목이 아니었다.

| | 이 구현 | LEANN |
|---|---|---|
| 벡터 저장 | int8, 구절당 768 바이트 | 수십 MB 수준 |
| 질의 1회 | 41만 구절 의미 검색 20–30 ms, 질의 임베딩까지 70–260 ms(M2 Max, Bun) | 논문 기준 RTX 4090에서 1.1–7.1초 |
| 최초 구축 | 모든 구절을 한 번 임베딩 | 같다 |
| 통합 | TypeScript + SQLite | Python + C++ 라이브러리(Boost, Protobuf, ZeroMQ, OpenBLAS) |

보고서 한 편에 검색을 수십–수백 번 하므로 질의 지연이 더 중요하다.

### 구절 나누기

- 문서 전체에서 가장 많이 쓰인 글자 크기를 본문으로 보고, 줄 간격·들여쓰기·짧은 마지막 줄·글자 크기 변화로 문단을 나눈다. 문장이 끝나지 않은 줄은 쪽이나 단을 넘어가도 같은 문단으로 잇는다.
- 위·아래 여백에서 여러 쪽에 되풀이되는 줄(러닝 헤드, 쪽 번호, 다운로드 표시)과 1쪽의 출판사 안내문, 링크만 있는 줄을 뺀다.
- 섹션 제목은 번호 붙은 제목, 흔한 섹션 이름(Introduction, Methods …), 본문보다 큰 글자이면서 바로 뒤에 본문이 오는 줄로 찾는다. 1쪽의 제목·저자·저널 배너는 섹션 이름으로 쓰지 않는다.
- 문서의 25%가 지난 뒤 나오는 References 제목에서 끊는다. 감사의 글·이해상충·기여도·자료 공개 같은 뒷부분은 다음 제목까지 뺀다.
- 구절은 문단을 모아 약 1,400자(최대 2,000자)로 만든다. 긴 문단은 문장 경계에서 자른다. 구절은 섹션을 넘지 않는다. 섹션 끝의 짧은 꼬리는 앞 구절에 붙이고, 제목 없는 앞부분만 첫 섹션으로 이어진다.
- 실제 서고 16편 표본에서 쪽당 3.15구절, 쪽당 본문 약 3,650자였다. 표의 숫자 행은 대부분 빠지고 표 제목과 주석은 남는다.

`CHUNKER_VERSION`을 올리면 모든 PDF를 다시 나누고 다시 임베딩한다(서고 전체 약 4시간).

### 저장과 검색

- 구절은 PDF의 내용 해시에 묶인다. 파일을 옮기거나 이름을 바꿔도 다시 색인하지 않는다. 서고 행이 더 이상 가리키지 않는 해시(앱에서 뺀 PDF 포함)의 구절은 다음 색인에서 지운다.
- 임베딩 입력은 `title: <논문 제목> | text: <섹션>. <구절>`(embeddinggemma 문서 형식)이다. 벡터의 모델 이름은 `<모델>@<digest>#<프롬프트 버전>`이라 모델을 바꾸면 구절이 다시 임베딩 대기로 돌아간다.
- 의미 검색은 모든 벡터의 부호 비트(평균을 뺀 뒤)를 메모리에 두고 Hamming 거리로 후보 3,000개를 고른 뒤, 그 int8 벡터를 읽어 정확한 코사인으로 다시 매긴다. 메모리는 구절 100만 개에 약 100 MB다. 폴더 범위는 스캔 안에서 걸러서 작은 폴더도 가까운 구절을 받는다.
- 어휘 검색은 FTS5 BM25(섹션 가중 2배)다. 검색어가 세 개 이상이면 그 절반 이상이 들어 있는 구절만 남기고, 든 단어가 많은 순서, 그다음 BM25 순서로 매긴다. 한국어 질문의 한 단어가 서고의 한국어 문서에만 걸려 맨 위로 오던 문제가 이것으로 사라졌다. 두 순위는 RRF(k=60)로 합치고, 한 논문에서 최대 3구절만 보여 준다.
- 다른 프로세스가 구절이나 벡터를 더하면 `meta.stamp`가 바뀌고, 5분이 지난 뒤의 검색에서 메모리 코드를 다시 읽는다. 결과 위의 색인 진행 수치도 `stamp`가 바뀔 때만 다시 센다(벡터 41만 개를 세는 데 약 0.1초).
- 앱을 켠 뒤 첫 본문 검색은 부호 비트를 읽느라 2.5초쯤 걸린다. 그동안 서비스 프로세스가 멈춘다.

### 증분 색인

- 앱에서는 서고가 시작된 뒤(앱 실행 중) 스캔이 끝날 때마다 한 번 돈다. 앱이 내려받은 PDF도 몇 초 안의 저장 스캔 뒤에 이어서 색인된다.
- 한 번의 실행은 PDF 두 개씩 읽어 나누고, 그동안 임베딩은 32구절씩 따로 진행한다. 추출이 임베딩보다 훨씬 빨라 대기열이 쌓인다.
- 서고가 마운트되지 않았으면 실패로 기록하지 않고 멈춘다. 읽지 못한 PDF와 텍스트가 없는 스캔본은 기록해 두고 다시 시도하지 않는다(나누는 규칙이 바뀌면 다시 시도한다).
- `meta.owner` 잠금(2분 만료, 30초마다 갱신)으로 앱과 `scripts/passages.ts`가 동시에 색인하지 않는다.
- 일시정지는 `passages.sqlite`에 저장되어 앱을 다시 켜도 유지된다.

## 명령줄 실행

```bash
bun scripts/build.ts
caffeinate -i bun scripts/passages.ts --worker <dist/runtime 사본>/pdf-worker.cjs
```

라이브러리는 읽기 전용으로 열고 `passages.sqlite`만 쓴다. `--limit N`은 앞의 N개 PDF만, `--out`은 다른 파일에 쓴다. 긴 실행 중에 앱을 다시 빌드하면 워커 파일이 바뀌므로 `dist/runtime`을 복사해 `--worker`로 넘긴다.

## 측정 (M2 Max, Ollama 0.40.11, embeddinggemma-2 MLX)

- 실제 구절 임베딩: 초당 약 29구절(구절당 272토큰). 추출과 함께 돌 때 초당 약 23구절. 동시 요청과 큰 배치는 빠르지 않았다.
- 줄 추출: NAS의 PDF 한 편에 0.3–3초. 서고 전체 추출은 임베딩보다 먼저 끝난다.
- 40편 시험 색인: 1,715구절, 파일 6.2 MB(본문 2.6 MB, 벡터 1.8 MB, FTS 1.4 MB).
- 서고 전체(2026-10-27 밤, 명령줄): PDF 9,055개 중 9,016개를 색인했다. 텍스트 없는 스캔본 3개, 읽지 못한 PDF 36개(암호화·손상·시간 초과)다. 구절은 417,730개, 평균 1,160자이고 8%는 섹션 이름이 없다. 4시간 49분 걸렸고(초당 약 24구절), 파일은 1.4 GB다.
- 일부 PDF는 글리프를 NUL 같은 제어 문자로 내보낸다(구절 4,542개). 지금은 워커가 이를 지우고, 이전에 나눈 구절은 검색 결과에서 지워 보여 준다. 단어 검색에는 영향이 없다.

## 다음 단계

- 2단계: 질문을 하위 질의로 나눠 구절을 찾고, 답의 인용은 찾아온 구절 ID로만 달게 한 뒤 인용문이 구절에 실제로 있는지 확인한다. 근거가 모자라면 모자라다고 답한다.
- 3단계: 계보 리포트의 개요 → 섹션 → 집필 → CSL 렌더링을 질문에서 시작하도록 바꾸고, 섹션마다 구절을 찾아 `[@citekey, p. N]`으로 인용한다.
- 스캔본 OCR(macOS Vision), 리더에서 구절 강조 표시.
- 첫 검색 전에 부호 비트를 나눠서 미리 읽어 두기(서비스가 멈추지 않게).
