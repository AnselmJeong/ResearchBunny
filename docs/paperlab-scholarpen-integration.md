# PaperLab 검토와 ResearchBunny · ScholarPen 공동 발전 방향

작성 2026-11-19. 제안서이며 구현된 것은 없다. 같은 날 사용자의 결정(10절)과 심사 목적(3절), 연동 상세(7–8절)를 반영해 고쳤다.

검토 대상과 근거:

- [PaperLab](https://github.com/khannoussi-malek/PaperLab) — 저장소를 내려받아 코드를 읽었다(실행하지 않음). Apache-2.0.
- ResearchBunny 0.4.0 — 이 저장소의 `src/`.
- ScholarPen 1.12.0 — `/Volumes/Aquatope/_DEV_/ScholarPen`(main, 3ef370e)과 공유 폴더 `_ScholarPen_`의 실제 프로젝트 두 개.
- Ollama 결정 모델 — [공식 문서](https://docs.ollama.com/capabilities/decision.md)만 읽었고 직접 호출해 보지는 않았다.

## 1. 결론

1. **LLM 관련성 심사는 도입한다.** 지금의 관련도는 TF-IDF 코사인과 OpenAlex 주제 겹침이라, 단어가 겹치는 엉뚱한 논문을 걸러낼 방법이 없다. 프로젝트마다 포함·제외 기준을 두고, 기준별로 판정한 뒤 아카이브에 넣을지 추천한다. 기준은 사용자가 일일이 쓰지 않고 AI가 초안을 만든다.
2. **결정 모델(말씀하신 "chef"는 Ollama의 `Clef`로 보인다)은 1차 판정에 잘 맞는다.** 기준 하나가 질문 하나가 되고 확률이 돌아온다. 다만 근거 문장을 주지 못하므로, 애매한 논문과 이유 설명은 생성 모델이 맡는 2단 구조를 권한다. 정확도는 내 아카이브로 측정한 뒤에 기본값으로 삼는다.
3. **논문별 근거 표는 도입한다.** 본문 구절 색인과 계보 카드가 이미 있어 PaperLab보다 좋은 조건이다. 열을 프로젝트마다 더할 수 있게 한다.
4. **프로젝트 폴더 공유는 "폴더를 연결"하는 방식으로 한다.** ResearchBunny의 SQLite를 Google Drive로 옮기지 않는다. ResearchBunny 프로젝트에 ScholarPen 프로젝트 폴더를 연결하고, 폴더에는 일반 파일만 쓴다.
5. **커넥터는 MCP 서버 하나로 만들되, ScholarPen의 LLM이 아니라 ScholarPen의 코드가 부른다.** ScholarPen의 내장 AI는 도구 호출이 없고 MCP를 일부러 꺼 두었으므로, 모델에게 도구를 쥐여 주는 방식은 쓰지 않는다. ScholarPen이 정해진 절차 안에서 커넥터를 호출하고, 외부 에이전트(Claude Code, Codex)는 같은 서버를 MCP로 쓴다. 연동은 한 방향이다: ScholarPen이 ResearchBunny의 프로젝트 아카이브를 쓴다.
6. **인용 검증은 새로 만들 필요가 없다.** ScholarPen에 `Check Citations`가 이미 있고 overclaim·오독 판정까지 한다. 부족한 것은 원문이다. 프로젝트 폴더에 PDF가 없는 인용은 초록만 보고 판정한다. ResearchBunny 서고(PDF 9,055개, 41만 7천 구절)를 그 원문 공급원으로 붙이는 것이 가장 값싼 큰 개선이다.

## 2. PaperLab은 무엇인가

FastAPI + Postgres(pgvector) + Redis 워커 + React 구성이고, 데스크톱 앱은 Docker Compose 스택을 띄우는 Electron 껍데기다. 기본 LLM은 Ollama `qwen3:8b`이며 OpenAI 호환·Anthropic도 지원한다. 기능은 논문 읽기, 체계적 문헌고찰, LaTeX 원고 작성을 한 앱에 모은 것이다.

우리와 관련된 부분을 코드에서 확인한 결과:

| 기능 | 실제 구현 | 평가 |
|---|---|---|
| 포함·제외 기준 | 워크스페이스에 자유 서술 3칸(연구 질문, 포함, 제외) | 기준별 판정이 없다. 어느 기준에 걸렸는지 알 수 없다 |
| AI 사전 심사 | 논문 1편당 호출 1회. 관련성 1–5, include/exclude/unsure, 제외 사유, 초록에서 그대로 옮긴 인용 최대 3개 | 한 편씩 순차 호출이라 느리다(작업 제한 4시간) |
| 신뢰도 | 인용문이 초록에 실제로 있는지만 본다. 없으면 "낮음" | 모델 확률이나 보정이 없다 |
| 사람 결정과 분리 | AI 제안은 별도 열. `Accept`를 눌러야 결정으로 복사. 기준을 바꾸면 제안을 모두 지운다 | **가져올 것** |
| 실패 처리 | 파싱 실패·초록 없음은 `unsure`. 제외로 가지 않는다 | **가져올 것** |
| 심사 순서 | ASReview식 TF-IDF + 나이브 베이즈로 사용자 결정을 학습해 정렬 | 수천 편 심사용. 우리 규모에는 불필요 |
| 정확도 검증 | 사용자의 실제 결정과 비교해 놓친 관련 논문 5% 이하일 때만 통과 | **가져올 것** |
| 근거 카드 | 고정 6열(연구 질문, 설계, 표본, 결과, 효과 크기, 한계). 열마다 구절을 검색해 한 번에 채운다 | 열을 더할 수 없고 논문당 1장(프로젝트별 아님) |
| 칸 검증 | 인용문이 구절에 그대로 있어야 하고, 값의 숫자가 모두 인용문에 있어야 한다. 실패한 칸은 비우고 센다 | **가져올 것** |
| 주장 검증 | supported / partially / not_supported / not_addressed. 근거가 전문인지 초록인지 기록 | ScholarPen에 이미 더 세분된 판정이 있다 |
| MCP 서버 | 도구 79개, 읽기·쓰기 표시, 호출 기록, 쓰기 전체 차단 스위치 | 구조는 참고, 규모는 과하다 |
| 종합 보고서 | 없다 | ResearchBunny의 계보 리뷰가 앞서 있다 |

가져오지 않을 것: Docker 스택, LaTeX 원고 작성(ScholarPen의 일), 읽기 진도 추적, 음성, 그래프 3D, PRISMA 흐름도(체계적 고찰을 실제로 쓸 때 다시 검토).

코드는 Python이라 그대로 옮길 것은 없고 설계와 프롬프트 문구만 참고한다. 프롬프트를 옮겨 쓰면 Apache-2.0 고지를 붙인다.

## 3. 제안 A — LLM 관련성 심사

### 지금의 문제

- `relatedness()`(`src/shared/domain.ts`)는 후보의 제목·초록과 연구 질문·초기 관심 문헌 사이의 TF-IDF 코사인, 그리고 OpenAlex 주제 겹침 중 큰 값을 쓴다. 관련성 필터의 문턱은 0.18 / 0.075 / 0.015다.
- 그래서 "clozapine"과 "augmentation"이 들어 있으면 동물 실험이든 다른 질환이든 높은 점수를 받는다. 질문의 의도(대상, 중재, 설계, 원하지 않는 것)는 점수에 들어가지 않는다.
- LLM 평가(`evaluate`, `src/service/providers/openai.ts`)는 `AI 탐색` 모드에서만, TF-IDF 상위 60편 중 20편을 고르는 데 쓴다. 일반 검색, 참고문헌·인용 확장, 관련 논문에는 없다. 고르지 않은 40편이 왜 빠졌는지도 남지 않는다.

### 설계

**심사 기준(프로젝트마다).** 연구 질문 한 줄로는 의도를 전달하기 어렵다. 프로젝트에 다음을 둔다.

- 의도: 무엇을 알고 싶은지, 무엇은 원하지 않는지 두세 문장.
- 포함 기준과 제외 기준: 각각 한 문장짜리 항목의 목록. PaperLab의 자유 서술 한 칸과 달리 항목이 따로 저장되어 항목마다 판정을 받는다.

기준은 **AI가 초안을 만들고 사용자는 고친다.** 재료는 연구 질문, 초기 관심 문헌, 그리고 지금까지의 결정(아카이브에 넣은 논문과 휴지통으로 보낸 논문)이다. 이후에도 추천된 논문을 사용자가 거절하면 "이 논문이 왜 아닌가"를 한 줄로 받아 제외 기준 후보로 제안한다. 일일이 지시하지 않아도 기준이 쌓인다.

**심사 목적.** 같은 질문이라도 계보 문서·종설을 쓰려고 모을 때와 원저 논문을 쓰려고 모을 때 원하는 논문의 성격이 다르다. 이것을 기준 문장에 섞어 쓰지 않고 따로 둔다. 판정을 두 축으로 나눈다.

- **주제 관련성**: 이 논문이 질문의 주제를 다루는가. 목적과 무관하다. 포함·제외 기준이 여기에 속한다.
- **역할 적합성**: 이 논문이 지금의 목적에 어떤 쓸모가 있는가. 목적에 따라 달라진다.

역할 적합성은 다시 둘로 나뉜다. 하나는 **논문의 성격**으로, 목적과 무관하게 한 번만 판정해 저장한다: 유형(종설·논평 / 체계적 고찰·메타분석 / 원저 / 주변 문헌 — 계보 리뷰가 이미 쓰는 `R·M·O·P`와 같다)과 기여(개념 정리, 출발점이 된 연구, 논쟁 정리, 방법 제시, 일차 자료, 반박). OpenAlex의 `type`과 PubMed 출판 유형으로 먼저 정하고, 모자란 것만 모델이 판정한다. 다른 하나는 **목적별 질문**이다.

| | 계보·종설 목적 | 원저 연구 목적 |
|---|---|---|
| 묻는 것 | 이 분야의 기본 개념과 흐름을 정리하는가 · 한 가설이나 연구 계열의 출발점인가 · 논쟁의 양쪽을 다루거나 한쪽을 반박하는가 · 어떤 계열이 버려지거나 살아남은 이유를 말하는가 | 질문에 대한 일차 자료를 보고하는가 · 대상과 설계가 내 연구와 비교할 만한가 · 다시 쓸 수 있는 방법·도구·패러다임을 제시하는가 · 효과 크기나 수치가 있는가 |
| 선호 | 종설, 개념·역사 논문, 메타분석, 많이 인용된 출발점 원저 | 원저, 방법 논문, 메타분석, 최근 후속 연구 |
| 덜 원하는 것 | 같은 결과를 되풀이한 소규모 원저 | 원자료 없는 서술적 종설, 논평 |
| 검색 | 종설 유형 우선, 피인용 순, 오래된 것도 포함 | 원저 우선, 최근 것, 설계·대상 용어 추가 |
| 근거 표 기본 열 | 문제의식, 주장, 입장, 미해결 문제(계보 카드와 같다) | 설계, 표본, 결과, 효과 크기, 한계 |

주의할 점은 목적이 유형 필터가 아니라는 것이다. 계보에도 원저가 필요하다(출발점, 결정적 반박). 그래서 "종설만 남긴다"가 아니라 "계보에서 맡을 역할이 있는가"를 묻는다.

쓰는 방식:

- 프로젝트에 기본 목적을 둔다(`계보·종설` / `원저 연구` / 직접 정의). 탐색을 시작할 때와 후보 목록에서 바꿀 수 있다.
- 주제 관련성과 논문의 성격은 목적을 바꿔도 다시 판정하지 않는다. 목적별 질문 몇 개만 새로 묻는다. 결정 모델로는 편당 요청 한 번이라 목적을 바꿔 보는 비용이 작다.
- 추천은 두 축을 합쳐 낸다. 주제는 맞지만 역할이 맞지 않는 논문은 제외가 아니라 `보류`이고, 이유를 "주제 관련 · 이 목적에는 일차 자료 없음"처럼 적는다. 주제가 어긋난 것과 구별된다.
- 아카이브는 프로젝트에 하나다. 담긴 논문마다 성격 표시(유형, 기여)가 붙고 필터 `논문 성격`으로 고른다. 계보 리뷰를 만들 때는 계보용 논문만, 원고의 방법 절을 쓸 때는 방법 논문만 꺼낸다. 한 프로젝트에서 종설과 원저 논문을 모두 쓰는 경우에도 아카이브를 둘로 나누지 않는다.
- 목적은 7절의 커넥터에서도 범위로 쓴다. ScholarPen이 "방법 논문 중에서", "종설 중에서" 근거를 찾을 수 있다.

**파이프라인.**

1. 수집과 1차 정렬은 지금 그대로다(OpenAlex·PubMed 검색, TF-IDF, 서고 임베딩). 값싸고 놓치지 않는 것이 목적이므로 여기서는 버리지 않는다.
2. 초록이 없는 후보는 PubMed·Europe PMC에서 채운다. 그래도 없으면 모델을 부르지 않고 `보류`로 둔다.
3. **1차 판정 — 결정 모델.** 후보 한 편당 요청 하나에 질문을 묶는다. 기준마다 `noul`(참일 확률 0–1) 하나, 전체 관련성 `score`(5단계) 하나. 응답은 수십 ms 단위의 숫자뿐이다.
4. **2차 판정 — 생성 모델.** 확률이 애매한 구간의 후보와, 추천으로 올라간 후보의 근거 문장만 처리한다. 20편씩 묶어 보내고, 판정·한 줄 이유·초록에서 그대로 옮긴 인용을 받는다. 사용자의 최근 수락·거절 예 몇 개를 프롬프트에 넣는다(PaperLab에 없는 부분).
5. 결과는 후보의 `evidence.screen`에 사람의 상태와 따로 저장한다: 추천(포함 / 보류 / 제외), 관련성, 기준별 판정, 이유, 인용, 모델, 프롬프트 버전, 기준 버전.

**화면.**

- 후보 목록에 추천 표시와 걸린 기준을 보인다("제외 기준 2: 동물 연구").
- 필터에 `AI 추천`을 더한다. 기존 규칙대로 필터는 맞는 것만 보여 주고, 제외 추천을 보려면 그 값을 고른다.
- `추천만 아카이브에 담기`는 사용자가 누를 때만 실행한다. 자동으로 담지 않는다.
- **기존 아카이브 점검.** 이미 담긴 논문을 같은 기준으로 심사해 기준에 맞지 않는 것을 보여 준다. 지금 끼어 있는 엉뚱한 논문을 찾는 데 바로 쓸 수 있다. 빼는 것은 사용자가 한다.

**지킬 규칙(PaperLab에서 확인한 것).**

- 파싱 실패, 응답 오류, 초록 없음은 `보류`다. 제외로 떨어지지 않는다.
- 제외는 초록이 기준을 분명히 어길 때만. 확실하지 않으면 보류.
- 인용문은 초록에 그대로 있어야 한다(기존 `validateRecommendations`와 같은 검사). 없으면 신뢰도를 낮춘다.
- 기준을 바꾸면 이전 추천은 무효로 표시한다.

### 결정 모델에 대한 판단

맞는 점:

- 과제가 분류다. 기준 하나에 예/아니오를 답하는 일에 수백 토큰의 산문을 생성할 이유가 없다.
- 확률이 나온다. 문턱을 조절할 수 있고, 애매한 구간만 큰 모델로 넘길 수 있다. 생성 모델이 말하는 "확신"보다 다루기 쉽다.
- 기준별 판정이 API 형태와 그대로 맞는다(`questions`에 기준마다 하나, 클라우드 요청당 최대 64개).
- 후보 300편을 모두 심사해도 부담이 없다. 지금 60편에서 자르는 제한이 사라진다.

걸리는 점:

- 문서에는 Nimble, Tev1, Clef, Clef Flash가 나온다. 정확도와 한국어 질문 처리, 이 분야 초록에서의 성능은 확인하지 못했다. 2차 자료에는 한 벤치마크에서 Nimble 74.8%라는 수치가 있는데, 논문 심사에 그대로 적용할 수 없다.
- 근거 문장을 주지 않는다. 왜 제외인지 보여 주려면 생성 모델이 필요하다.
- 호출은 클라우드로 한다(결정됨): `https://ollama.com/v1/systemone`에 API 키로 직접 보낸다. ResearchBunny에는 Ollama Cloud 키 저장과 호출 코드(`src/service/providers/ollama.ts`)가 이미 있어 엔드포인트 하나를 더하는 일이다. 문서상 클라우드 입력 한도는 Clef의 65,536 토큰, 요청당 질문 64개이고 입력 토큰으로 과금된다. 보내는 것은 공개된 제목·초록과 사용자의 심사 기준이다.

그래서 순서를 이렇게 잡는다. 먼저 **평가 세트**를 만든다. 기존 프로젝트의 아카이브(관련 있음)와 휴지통·제거한 후보(관련 없음)가 정답이다. 결정 모델 단독, 생성 모델 단독(지금 쓰는 Codex 구독 모델), 2단 구조를 같은 세트로 비교한다. 통과 조건은 관련 논문을 놓치는 비율 5% 이하. 이 수치로 기본 구성을 정한다. 결정 모델이 기준에 못 미치면 생성 모델 일괄 판정으로 가고, 구조는 그대로 쓴다.

## 4. 제안 B — 논문별 근거 표

연구 질문, 설계, 표본, 결과, 한계를 논문마다 표로 정리하는 기능이다. 재료는 이미 있다.

- 본문 구절 색인(`passages.sqlite`): 쪽 번호가 붙은 구절, 하이브리드 검색.
- 계보 카드(`src/service/genealogy/cards.ts`): 논문 한 편에서 문제·주장·근거(원문 인용 포함)·비판을 뽑는 구조와 검증.

설계:

- 기본 열: 연구 질문, 설계, 표본(n, 대상), 주요 결과, 효과 크기, 한계. **프로젝트마다 열을 더한다**(예: 용량, 추적 기간, 평가 도구). 열은 이름과 "무엇을 찾는가" 한 줄로 정의한다. PaperLab은 고정 6열이다.
- 채우는 방식: 열마다 그 논문의 구절을 검색해 상위 구절을 모으고(쪽·섹션 표시), 논문 한 편당 한 번 호출한다.
- 칸마다 값, 원문 인용, 쪽을 저장한다. 인용이 구절에 그대로 없거나 값의 숫자가 인용에 없으면 칸을 비우고 표시한다. 채워 넣지 않는다.
- PDF가 없는 논문은 초록으로 채우고 `초록 기반`으로 표시한다. 원문이 확보되면 다시 채운다.
- 표는 프로젝트별이다. 같은 논문도 프로젝트의 질문에 따라 "주요 결과"가 달라진다.
- 칸을 누르면 원문의 그 쪽이 열린다(구절 검색 결과와 같은 동작).
- 내보내기: CSV(긴 형식)와 Markdown 표. 연결된 ScholarPen 프로젝트 폴더에도 쓴다(6절).

이 표는 심사와도 이어진다. 원문 단계의 포함·제외(설계나 표본이 기준에 맞는가)를 판정할 때 표의 칸이 근거가 된다.

## 5. 두 앱의 현재 모습

| | ResearchBunny | ScholarPen |
|---|---|---|
| 프로젝트 | 라이브러리 SQLite의 행(이름, 연구 질문). 폴더가 아니다 | 공유 폴더의 하위 폴더 하나(점으로 시작하지 않는 모든 폴더) |
| 문헌 목록 | `works` + 프로젝트별 상태 | 프로젝트별 `exports/references.bib` |
| 인용 연결 | DOI·PMID·OpenAlex ID | 원고의 citation 노드는 citekey만 가진다. DOI는 bib 항목에 있다 |
| PDF | 서고 한 곳(전 프로젝트 공용) | `resources/articles/`의 PDF만 읽는다. 내려받지 않는다 |
| 원문 검색 | 구절 색인 41만 개, 의미 + 어휘 | 프로젝트 PDF의 FTS(`db/citation-sources.sqlite`) |
| 원문 확보 | 앱의 Chrome으로 내려받기 | 없음. "PDF 없는 인용" 목록만 보여 준다 |
| 인용 검증 | 없음 | `Check Citations`: supported / partial / overclaim / contradicted / unsupported / unverifiable, 원문 인용 확인 |
| 인용 찾기 | 근거를 달아 답하기(구절 기반) | `Find citation`: Paperclip API, OpenAlex·Crossref |
| AI | Ollama Cloud, Codex·Claude 구독, OpenAI | Ollama, Claude·Codex 구독, DeepSeek, OpenAI |
| 도구 호출·MCP | 없음 | 없음. 구독 CLI에서 MCP와 도구를 꺼 둠 |

두 앱은 겹치는 부분이 거의 없고 서로 빈 곳을 채운다. ScholarPen에는 원문과 원문 확보가 없고, ResearchBunny에는 원고가 없다.

공유 폴더에 대해 확인한 것:

- 루트의 `AGENTS.md`·`CLAUDE.md`·`GEMINI.md`는 Tolaria 볼트용 안내다. ScholarPen 코드는 읽지 않는다.
- ScholarPen은 프로젝트 목록을 읽을 때 점으로 시작하지 않는 모든 폴더에 `documents/`를 만든다.
- 파일 트리는 점으로 시작하는 폴더를 숨긴다. `.researchbunny/`는 보이지 않고 색인되지도 않는다.
- 프로젝트 루트에 `references.bib`를 두면 ScholarPen이 `exports/references.bib`로 합치고 지운다.
- `resources/` 아래의 PDF는 자동으로 색인된다.

## 6. 제안 C — 프로젝트 폴더 공유

"같은 폴더에 프로젝트를 둔다"는 생각은 그대로 살리되, 저장소를 합치지는 않는다.

**하지 않을 것: ResearchBunny의 SQLite를 Google Drive에 두기.** 동기화 중인 폴더의 SQLite(WAL)는 쓰는 쪽이 둘이면 깨질 수 있다. 또 ResearchBunny의 라이브러리와 서고는 프로젝트 전체가 공유하는 하나의 저장소라 프로젝트 폴더로 쪼갤 수 없다.

**할 것: 프로젝트에 폴더를 연결한다.**

- ResearchBunny 설정에 공유 폴더 루트(`_ScholarPen_`)를 지정한다. 이 루트의 폴더는 모두 ScholarPen 프로젝트이므로(결정됨) 전부 연결 후보로 보인다.
- ResearchBunny 프로젝트마다 `연결된 폴더` 하나를 둔다. 프로젝트를 만들 때 같은 이름의 폴더를 새로 만들거나 기존 폴더를 고른다. 폴더 하나에 ResearchBunny 프로젝트 하나다.
- ScholarPen은 그 폴더를 자기 프로젝트로 본다. 한쪽 앱에서 만든 프로젝트가 다른 쪽에 나타난다.
- 폴더에는 일반 파일만 쓰고, **파일마다 쓰는 앱은 하나**로 정한다.

| 경로 | 쓰는 앱 | 내용 |
|---|---|---|
| `documents/*.scholarpen.json` | ScholarPen | 원고 |
| `exports/references.bib` | ScholarPen | 인용 목록. ResearchBunny는 읽기만 하고, 추가는 커넥터로 BibTeX를 건네 ScholarPen이 합친다 |
| `.researchbunny/project.json` | ResearchBunny | 연결 정보: ResearchBunny 프로젝트 ID, 연구 질문, 심사 목적과 기준 |
| `.researchbunny/archive.json` | ResearchBunny | 아카이브 목록: DOI, PMID, 제목, 연도, 논문 성격, 컬렉션·소주제, PDF·색인 여부 |
| `.researchbunny/evidence.csv`, `evidence.md` | ResearchBunny | 근거 표 |

PDF 사본은 프로젝트 폴더에 두지 않는다(결정됨). PDF는 중앙 서고에만 있고, ScholarPen은 원문을 커넥터로 읽는다. 따라서 ScholarPen이 서고에 있는 논문의 원문을 쓰려면 이 Mac에서 커넥터가 돌아야 한다. 다른 기기에서는 `.researchbunny/`의 목록과 근거 표까지만 쓸 수 있다.

**한쪽 앱만 쓰는 경우.**

- ScholarPen만: 연결되지 않은 프로젝트는 지금과 똑같이 동작한다.
- ResearchBunny만: 폴더를 연결하지 않고 지금처럼 쓴다. 연결은 선택이다.
- ScholarPen 프로젝트가 먼저 있는 경우: ResearchBunny에서 `폴더에서 프로젝트 만들기`를 하면 `references.bib`를 가져와 아카이브를 채우고(BibTeX 가져오기는 이미 있다), PDF 없는 것의 원문 확보를 제안한다.

**연결의 열쇠.** ScholarPen의 인용은 citekey → bib 항목의 DOI·PMID로 이어지고, ResearchBunny는 DOI·PMID로 문헌을 찾는다. 순서는 DOI, PMID, 정규화한 제목 + 연도다. ResearchBunny의 citekey 규칙(`citekeyFor`)은 ScholarPen의 키와 다르므로 ResearchBunny는 키를 만들거나 바꾸지 않는다. 아카이브에 있으나 `references.bib`에 없는 논문은 ScholarPen이 인용을 넣는 순간 자기 규칙으로 키를 만든다.

## 7. 제안 D — 커넥터

### 방향

연동은 한 방향이다. **ScholarPen이 ResearchBunny의 특정 프로젝트에 모인 아카이브나 컬렉션을 근거로 글쓰기를 돕는다.** ResearchBunny가 ScholarPen의 기능을 쓰는 일은 거의 없으므로 만들지 않는다. ResearchBunny가 하는 일은 자료를 잘 모으고(3절), 정리하고(4절), 내주는 것이다.

### 왜 닫힌 집합에서 찾는 것이 나은가

ScholarPen의 `Find citation`은 지금 외부 API(Paperclip, OpenAlex, Crossref)에서 수백만 편을 상대로 찾고, 초록만 보고 고른다. 프로젝트 아카이브에서 찾으면 다음이 달라진다.

- 후보가 수백 편이다. 구절로는 수천 개라 전부 훑어도 수십 ms다.
- 사용자가 이미 심사해 담은 논문이다. 주제가 어긋난 논문이 나오지 않는다.
- 초록이 아니라 본문 구절을 쪽 번호와 함께 준다. 인용할 문장을 직접 볼 수 있다.
- 논문 성격과 근거 표가 붙어 있어 "이 주장에는 종설보다 원자료가 낫다" 같은 선택을 할 수 있다.
- 결과가 사용자의 서고에 있으므로 눌러서 원문을 바로 열 수 있다.

외부 검색은 아카이브에서 찾지 못했을 때의 다음 단계로 남긴다.

### 구조

```
ScholarPen (Bun 프로세스)
   │  자식 프로세스로 실행, stdio, MCP
   ▼
researchbunny-connector ──읽기 전용──▶ 라이브러리 SQLite · passages.sqlite · 서고 PDF
   ▲                                    (ResearchBunny 앱이 켜져 있지 않아도 된다)
   │  같은 프로그램, 같은 도구
Claude Code · Codex (공유 폴더에서 작업할 때)
```

- 커넥터는 ResearchBunny 앱 번들에 들어 있는 작은 프로그램이다. ScholarPen이 필요할 때 자식 프로세스로 띄우고 stdio로 통신한다. 포트도 토큰도 없다.
- 통신 규약은 MCP다. 다만 ScholarPen에서 도구를 부르는 것은 모델이 아니라 ScholarPen의 코드다. 아래 작업 흐름마다 "어느 시점에 어떤 도구를 부른다"가 정해져 있다. 그래서 ScholarPen의 구독 CLI가 MCP를 꺼 둔 것과 충돌하지 않고, 결과가 실행마다 달라지지도 않는다.
- 외부 에이전트는 같은 프로그램을 MCP 서버로 등록해 쓴다. 한 번 만들어 두 곳에서 쓴다.
- **앱이 꺼져 있어도 읽기는 된다.** 커넥터가 라이브러리와 구절 색인을 읽기 전용으로 직접 연다. ResearchBunny 앱이 동시에 켜져 있어도 SQLite 읽기는 문제없다(두 저장소 모두 로컬 디스크에 있다). `scripts/passages.ts`가 이미 앱 밖에서 구절 색인을 열고 있어 구절 쪽은 확인된 방식이고, 라이브러리 읽기 경로를 서비스에서 떼어 내는 작업이 필요하다.
- 의미 검색에는 질의 임베딩이 필요하다. 로컬 Ollama(`embeddinggemma`)가 켜져 있으면 의미 + 어휘 검색, 꺼져 있으면 어휘 검색만 한다. 지금의 서고 검색과 같은 동작이다.
- 쓰기는 하나뿐이다(원문 확보 요청). 커넥터가 직접 내려받지 않고 요청을 대기열에 적는다. ResearchBunny 앱이 켜져 있거나 다음에 켜질 때 처리한다. Chrome 로그인과 내려받기는 앱만 한다.
- 범위는 항상 프로젝트다. ScholarPen은 열려 있는 프로젝트 폴더의 `.researchbunny/project.json`에서 ResearchBunny 프로젝트 ID를 읽어 넘긴다. 연결되지 않은 폴더에서는 커넥터를 부르지 않는다.
- PaperLab에서 가져올 것: 도구마다 읽기·쓰기 표시, 호출 기록.

### 도구

모든 읽기 도구는 `scope`를 받는다: 프로젝트 아카이브 전체, 컬렉션, 소주제, 논문 성격(예: 방법 논문만), 문헌 ID 목록, 또는 서고 전체.

| 도구 | 종류 | 하는 일 |
|---|---|---|
| `list_scopes` | 읽기 | 프로젝트의 컬렉션·소주제와 편수 |
| `list_works` | 읽기 | 범위 안의 문헌: 서지, 논문 성격, PDF·색인 여부, 근거 표 요약 |
| `resolve_works` | 읽기 | DOI·PMID·제목 → 라이브러리에 있는지, PDF가 있는지, 색인되었는지 |
| `find_support` | 읽기 | 주장 문장 → 범위 안에서 뒷받침하거나 반박하는 구절(문헌, 쪽, 섹션, 점수) |
| `search_passages` | 읽기 | 자유 질의 → 구절 |
| `get_passages` | 읽기 | 한 문헌의 구절을 쪽 범위로 |
| `get_evidence` | 읽기 | 한 문헌의 근거 표 칸(값, 원문 인용, 쪽) |
| `search_conversations` | 읽기 | 프로젝트에서 나눈 AI 대화를 질의나 문헌으로 찾기(8절 ④) |
| `get_bibtex` | 읽기 | 문헌의 BibTeX(키는 호출한 쪽이 정한다) |
| `request_fulltext` | 쓰기 | DOI 목록을 프로젝트에 담고 원문 확보를 대기열에 넣기 |
| `job_status` | 읽기 | 원문 확보·색인 진행 |

판정(주장이 뒷받침되는가, 인용할 만한가)은 커넥터에 두지 않는다. ScholarPen의 판정기가 이미 있고, 한 곳에만 있어야 결과가 어긋나지 않는다. 커넥터는 검색하고 원문을 준다. LLM을 부르지 않으므로 빠르고 비용이 없다.

## 8. ScholarPen에서 달라지는 것

### ① 쓰는 중에 인용을 안내한다

"이 문장은 아카이브의 어느 논문 몇 쪽에 근거가 있으니 인용하라"는 안내다. 새 기능을 더하는 것이 아니라, 지금의 `Find citation`이 외부 API 대신 연결된 ResearchBunny 프로젝트의 논문 목록에서 찾도록 바꾼다(결정됨). **사용자가 글을 선택하고 팝업 메뉴에서 요청할 때만 실행한다.** 자동으로 돌지 않는다. ScholarPen에 있는 부품을 거의 그대로 쓴다.

1. **대상은 선택한 글이다.** 선택 구간을 주장 1–3개로 바꾸는 코드는 이미 있다(`citation-claims.ts`).
2. **아카이브에서 찾는다.** 주장마다 `find_support`를 부른다. 범위는 사이드바에서 고른 것(기본은 프로젝트 아카이브 전체)이다. 한국어 원고의 주장은 이미 영어 주장문으로 바뀌어 넘어간다.
3. **판정한다.** 주장과 구절을 LLM에 보내 "이 구절이 이 주장을 직접 뒷받침하는가"를 묻는다. `Check Citations`의 판정기와 원문 인용 검사(인용문이 구절에 그대로 있어야 한다)를 그대로 쓴다. 뒷받침하지 않는 후보는 버린다.
4. **보여 준다.** 문장 옆에 제안이 뜬다: 논문, 쪽, 원문 한 문장, 논문 성격, 근거 표의 설계·표본. 원문 열기는 ResearchBunny의 그 쪽으로 간다.
5. **넣는다.** 수락하면 `[@key]`가 들어간다. `references.bib`에 없는 논문이면 `get_bibtex`로 받아 ScholarPen이 합친다(기존 `addEvidenceCitation` 경로).

같은 검색에서 반대 근거도 나온다. 아카이브의 구절이 선택한 문장과 어긋나면 "Lee 2021 7쪽은 반대 결과를 보고한다"고 알린다. 인용을 넣기 전에 문장을 고칠 기회다.

아카이브에서 찾지 못했을 때 외부 검색으로 넘어갈지는 ScholarPen 쪽 작업을 할 때 정한다.

### ② AI 사이드바가 아카이브를 안다

ScholarPen의 사이드바는 답하기 전에 맥락을 모은다(`context-builder.ts`): 현재 문서, 언급한 파일, 프로젝트 자료 요약, OpenAlex·PubMed 검색 결과. 여기에 `search_passages` 결과를 하나 더 넣는다.

- 질문과 현재 문단으로 프로젝트 아카이브를 검색해 구절 몇 개를 `[R1] Smith 2019, p. 7` 형태로 넣는다.
- 모델은 이 표지로만 인용한다. 답의 `[R1]`은 ScholarPen이 citekey로 바꾼다.
- "이 절에 무엇을 더 써야 하나", "이 주장에 반론이 있나" 같은 질문에 아카이브의 본문으로 답한다.

지금 있는 `Project Sources`(프로젝트 폴더의 요약 파일을 읽는 기능)와 같은 자리, 같은 방식이다. 사용자가 사이드바에서 범위를 고른다: 아카이브 전체, 컬렉션, 종설만, 방법 논문만.

### ③ 인용 검증에 서고 원문을 쓴다

`Check Citations`의 원문 순서를 프로젝트 PDF → 커넥터의 구절 → OpenAlex 초록으로 바꾼다. 확장 지점은 이미 있다(`CitationCheckDeps`, `Source` 구분에 값 하나 추가). PDF를 프로젝트 폴더에 두지 않기로 했으므로, 앞으로는 커넥터가 사실상 유일한 전문 공급원이 된다.

- 인용된 논문의 DOI로 `resolve_works`, 있으면 그 논문으로 범위를 좁혀 `find_support`.
- 판정 종류(supported / partial / overclaim / contradicted / unsupported / unverifiable)와 원문 인용 검사는 그대로다.
- 판정할 때 `get_evidence`의 설계·표본·한계를 함께 준다. "개방 연구 12명을 근거로 단정했다" 같은 overclaim은 본문 구절만으로는 놓치기 쉽고 표본과 설계가 있으면 드러난다.
- 결과에 근거가 전문인지 초록인지 표시하는 것은 이미 있다. 초록만 보고 내린 판정은 그렇게 표시된다.

### ④ ResearchBunny에서 나눈 대화를 참고한다

ResearchBunny의 AI 대화는 이미 프로젝트와 논문에 묶여 저장된다(`chat_threads`: 프로젝트, 문헌, 맥락). PDF를 읽다가 나눈 대화는 "어느 프로젝트에서 어느 논문을 읽으며"가 기록되어 있다. 커넥터가 이것을 내준다.

- `search_conversations(질의 또는 문헌)` → 대화의 질문·답 쌍, 날짜, 대상 논문, 당시 보던 구절의 쪽.
- **인용 위에서.** 원고의 인용을 누르면 "이 논문을 읽으며 나눈 대화 3건"이 보인다. 그때 떠올린 생각을 다시 찾을 수 있다.
- **사이드바에서.** 질문과 가까운 대화를 맥락에 `[N1] 2026-11-02, Smith 2019를 읽으며`로 넣는다. 구절(`[R#]`)과 표지를 달리한다. 대화는 사용자의 생각과 AI의 설명이지 문헌 근거가 아니므로, 모델이 이것을 출처로 인용하지 못하게 한다. 근거가 필요하면 대화에 기록된 구절을 다시 찾아 `[R#]`로 인용한다.

대화의 요지를 따로 만들지 않는다(결정됨). 저장된 대화를 그대로 검색해 가까운 질문·답 쌍을 돌려준다. 대화가 쌓여 잡음이 문제가 되면, 답 하나를 사용자가 직접 `메모로 남기기`로 표시하고 커넥터가 메모를 먼저 돌려주는 방법을 그때 검토한다.

대화를 Markdown 파일로 프로젝트 폴더에 내보내는 방법도 가능하다. ScholarPen의 `@파일` 언급으로 코드 변경 없이 읽힌다. 다만 대화가 고쳐질 때마다 Drive에 파일을 다시 써야 하고 대화가 두 곳에 있게 되므로, 기본은 커넥터로 읽는 쪽으로 한다.

### ⑤ 원문 없는 인용을 확보한다

ScholarPen의 `PDF 없는 인용` 목록에 `ResearchBunny에서 원문 확보`를 둔다. `request_fulltext`로 DOI를 넘기면 대기열에 들어가고, ResearchBunny 앱이 프로젝트에 담아 Chrome으로 내려받고 서고에 넣어 색인한다. 끝나면 ③이 전문으로 다시 판정한다. 외부에서 새로 찾아 인용한 논문도 이 경로로 아카이브에 들어와, 다음부터는 ①과 ②의 대상이 된다.

### ⑥ 외부 에이전트

공유 폴더에서 Claude Code나 Codex로 작업할 때 같은 도구를 MCP로 쓴다. 원고 한 장을 통째로 점검하거나 근거 표를 원고의 표로 옮기는 일은 여기서 한다.

### 만들지 않는 것

ResearchBunny가 원고를 읽어 `원고에 인용됨`을 표시하거나 원고에서 심사 기준을 뽑는 기능은 넣지 않는다. ResearchBunny에서 ScholarPen을 쓸 일이 드물기 때문이다. `폴더에서 프로젝트 만들기`(6절)가 `references.bib`를 한 번 읽는 것이 유일한 예외다.

## 9. 순서

| 단계 | 앱 | 내용 | 크기 |
|---|---|---|---|
| 0 | ResearchBunny | 평가 세트(아카이브 대 휴지통)를 만들고 결정 모델·생성 모델·2단 구조를 비교 | 작다 |
| 1 | ResearchBunny | 심사 목적과 기준(AI 초안), 논문 성격 판정, 후보 심사, 추천 표시·필터, 기존 아카이브 점검 | 크다 |
| 2 | ResearchBunny | 근거 표: 목적별 기본 열 + 프로젝트 열, 칸 검증, 내보내기 | 중간 |
| 3 | ResearchBunny | 폴더 연결, `.researchbunny/` 쓰기, `폴더에서 프로젝트 만들기` | 작다 |
| 4 | ResearchBunny | 커넥터: 읽기 도구(`list_*`, `resolve_works`, `find_support`, `search_passages`, `get_passages`, `get_bibtex`) | 중간 |
| 5 | ScholarPen | 인용 안내(①)와 인용 검증의 원문 공급원(③) | 중간 |
| 6 | ScholarPen | 사이드바의 아카이브 맥락(②), 범위 선택 | 작다 |
| 7 | 둘 다 | 대화 참고(④): `search_conversations` | 작다 |
| 8 | 둘 다 | 원문 확보 대기열(⑤), 근거 표 연동(`get_evidence`), 외부 에이전트 등록(⑥) | 중간 |

1과 2는 ScholarPen과 무관하게 ResearchBunny 혼자 좋아지는 부분이고 처음 지적한 문제(엉뚱한 논문)를 직접 다룬다. 4와 5가 연동의 핵심이다. 4는 1·2 없이도 만들 수 있으므로(구절 색인과 아카이브는 이미 있다), 인용 안내를 먼저 쓰고 싶으면 0–2보다 3–5를 앞세워도 된다. 그 경우 논문 성격과 근거 표가 없는 채로 시작하고 나중에 붙는다.

5단계부터는 ScholarPen 저장소의 변경이며 나중에 한다(결정됨). 그쪽에서 별도 작업으로 진행한다. 그 전까지 ResearchBunny 쪽에서 할 수 있는 것은 0–4다.

## 10. 정한 것

| | 결정 |
|---|---|
| 아카이브에 담기 | AI는 추천만 한다. 담는 것은 사용자가 한다. 자동 담기 옵션은 두지 않는다 |
| 결정 모델 | 클라우드. `ollama.com/v1/systemone`에 API 키로 호출한다 |
| PDF | 중앙 서고에만 둔다. 프로젝트 폴더에 사본을 만들지 않는다 |
| 공유 폴더 | `_ScholarPen_`의 폴더는 모두 ScholarPen 프로젝트다. 전부 연결 후보로 보인다 |
| 연동 방향 | ScholarPen이 ResearchBunny의 프로젝트 아카이브·컬렉션을 쓴다. 반대 방향은 만들지 않는다 |
| 심사 목적 | 프로젝트 기본값을 두고 탐색마다 바꾼다. 아카이브는 하나, 논문 성격으로 고른다 |

| 인용 안내 | 글을 선택하고 팝업 메뉴에서 요청할 때만 실행한다. 자동 실행은 없다 |
| ScholarPen의 인용 추천 | 지금의 `Find citation`을 연결된 ResearchBunny 프로젝트의 논문 목록에서 찾도록 바꾼다. 나중에 한다 |
| 대화 요지 | 만들지 않는다. 저장된 대화를 그대로 검색한다 |

남은 것: ResearchBunny 쪽 작업(0–4)을 어디서부터 시작할지.
